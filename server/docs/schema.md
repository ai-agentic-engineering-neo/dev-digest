# Database schema

Drizzle over Postgres with pgvector. One file per domain in
[`../src/db/schema/`](../src/db/schema), re-exported from `src/db/schema.ts`.

> **The schema already contains every table the course will ever use.** Tables belonging
> to a lesson that has not been built yet simply sit empty. An empty table is not a bug
> and not an invitation to drop it.

## Migrations

Generated by drizzle-kit into [`../src/db/migrations/`](../src/db/migrations):

```sh
pnpm db:generate   # edit src/db/schema/*.ts first, then generate
pnpm db:migrate    # apply — NOT run automatically on boot
pnpm db:seed       # idempotent demo data
```

**Rules that are not optional:**

- **Never hand-edit** a generated `.sql` file, `meta/_journal.json`, or a snapshot.
  Change the schema and regenerate.
- The journal, the `.sql` files and `meta/*_snapshot.json` must always agree: same
  count, tags in order, each snapshot's `prevId` pointing at the previous one.
- **Append, never rewrite.** On a merge conflict, renumber your migrations to sit after
  the incoming ones and relink the snapshot chain — do not take one side wholesale. See
  [`../INSIGHTS.md`](../INSIGHTS.md) for what this failure looks like in CI.
- Verify against a **fresh** database (the integration lane's testcontainer), because an
  already-migrated dev DB never replays broken history.

## pgvector

The `vector` extension is enabled by migration `0000`. `vector` type errors almost
always mean migrations ran against a different database than the one you are querying.
