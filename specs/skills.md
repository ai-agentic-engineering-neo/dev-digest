# Skills — специфікація фічі

Скіл — це іменований блок інструкцій у markdown, який **перевикористовується
між агентами**. Агент = провайдер + модель + system prompt + **впорядкований
набір скілів**. Скіл не виконує коду: у продукті це виключно текст конфігурації,
який потрапляє в промпт окремим блоком.

Дизайн: `i/img.png` (Config), `i/img_1.png` (Preview), `i/img_2.png` (Evals),
`i/img_3.png` (Stats), `i/img_4.png` (Versions), `i/img_5.png` (імпорт),
`i/img_6.png` (вкладка Skills у редакторі агента).

Половини спеки по пакетах: [`server/specs/skills-module.md`](../server/specs/skills-module.md),
[`client/specs/skills-ui.md`](../client/specs/skills-ui.md).
Контрольний експеримент: [`skills-control-experiment.md`](skills-control-experiment.md).

## Межі фічі

| У межах | Поза межами |
|---|---|
| CRUD скілів у БД (джерело правди), версії тіла | виконання будь-якого коду зі скіла |
| Прив'язка скілів до агента, порядок, увімкнення | RAG-пошук скілів під конкретний диф |
| Імпорт із `.md` та з архіву (`.zip`) через прев'ю | встановлення залежностей зі скіла |
| Вбудований каталог community-скілів (офлайн) | мережевий пошук по GitHub |
| Блок скілів у зібраному промпті + у трасі прогону | Evals-вкладка скіла (окрема фіча eval) |

## Модель даних

Таблиці вже є в схемі (`server/src/db/schema/skills.ts`, `.../agents.ts`) і досі
порожні:

- `skills` — `id, workspace_id, name, description, type, source, body, enabled,
  version, evidence_files, created_at`
- `skill_versions` — `(skill_id, version) PK, body, created_at` **+ нова колонка
  `note`** (що змінилось; опційна)
- `agent_skills` — `(agent_id, skill_id) PK, order`

`type` ∈ `rubric | convention | security | custom`;
`source` ∈ `manual | imported_url | extracted | community`.

Рішення: **прив'язка = увімкнення для агента**. Окремого прапорця в
`agent_skills` немає: галочка в редакторі агента створює/знімає зв'язок, а
глобальний перемикач на картці скіла (`skills.enabled`) вимикає скіл одразу для
всіх агентів. Обидва шляхи ведуть до одного спостережуваного результату — блок
у промпті є або його немає.

## Життєвий цикл скіла

```
створення (UI) ─┐
імпорт .md/.zip ─┼─► skills (enabled=true|false) ─► agent_skills ─► промпт прогону
каталог community ┘        │
                            └─► skill_versions (кожне збереження тіла = нова версія)
```

- Створення вручну → `source='manual'`, `enabled=true`, `version=1`, знімок v1.
- Імпорт → **спочатку прев'ю, збереження лише після підтвердження**;
  `source='community' | 'imported_url'`, `enabled=false` («needs vetting»).
- Редагування тіла → `version+1` і новий рядок у `skill_versions` з нотаткою.
- Відновлення старої версії → **нова** версія з тим самим тілом (історія не
  переписується).

## Опис як інтерфейс скіла

`description` — це не маркетинговий рядок, а **інтерфейс**: за ним агент (і
людина) вирішує, коли скіл доречний. Формулюємо директивно, у теперішньому часі,
починаючи з дієслова: «Detects…», «Flags…», «Requires…». На UI це закріплено
підписом під полем, а не лише в документації.

## Довіра до чужого скіла

Чужий скіл — це **чужі інструкції в промпті твого агента**. Продукт не робить
вигляд, що це безпечно:

1. Імпорт ніколи не зберігає одразу — спочатку прев'ю саме того тексту, який
   піде в промпт.
2. З архіву беремо **тільки ядро скіла** (`SKILL.md` / перший `*.md`, і
   frontmatter). Усе виконуване (`*.sh`, `*.js`, `*.py`, `hooks/`, `scripts/`,
   `*.yml`) не розпаковується і не зберігається — перелік пропущених файлів
   показано в прев'ю.
3. Імпортований скіл приходить **вимкненим**; увімкнути його — свідома дія
   користувача.
4. У блоці промпта кожен скіл підписаний іменем, типом і джерелом, тож у трасі
   видно, чий саме текст отримала модель.
5. `INJECTION_GUARD` рушія лишається на місці: диф, тіло PR і похідний контекст
   і далі є даними, а не інструкціями.

Свідомий компроміс: увімкнений імпортований скіл працює як **інструкція**, а не
як `<untrusted>`-дані. Інакше фіча не має сенсу (скіл не впливав би на ревʼю).
Захист — не в обгортці, а в тому, що вмикання лишається явним і оборотним.

## Скіли в промпті

Резолвер у `run-executor` бере впорядковані зв'язки агента, лишає тільки
`skills.enabled = true`, рендерить кожен у блок і віддає рушію як
`skills: string[]`. `assemblePrompt` уже вміє секцію `## Skills / rules` і кладе
її у `prompt_assembly.skills` траси.

```
### Skill: test-coverage-rubric (rubric · manual)
<тіло скіла як є>
```

Порядок блоків = порядок `agent_skills.order`. Вимкнений скіл не дає блоку і
окремо згадується в логах прогону рядком «skipped (disabled)».

## Екрани

| Екран | Маршрут | Що робить |
|---|---|---|
| Skills | `/skills?skill=<id>&tab=<tab>` | список ліворуч, деталь праворуч |
| Config | `?tab=config` | назва, опис, тип, тіло (markdown-редактор), Enabled, Save |
| Preview | `?tab=preview` | тіло, відрендерене так, як його бачить агент |
| Stats | `?tab=stats` | скількома агентами використовується + перехід до них |
| Versions | `?tab=versions` | історія версій, нотатки, Restore |
| Add Skill | drawer | «Create from scratch» / «Import from file» / «Community» |
| Agent → Skills | `/agents/:id?tab=skills` | прив'язка, порядок, лічильник |

Evals-вкладка і метрики «pull frequency / accept rate / findings 30d» з дизайну
**не реалізуються**: під ними немає даних, а вигадані числа зробили б екран
брехливим. Stats показує лише те, що справді виводиться з БД.

## Критерії приймання

Стан кожного пункту зі свідченнями — у
[`homework-2-acceptance.md`](homework-2-acceptance.md).

1. Скіл створюється й редагується в UI; БД — джерело правди (перезавантаження
   сторінки нічого не втрачає).
2. Список скілів показує назву, тип, опис, джерело і перемикач; клік відкриває
   деталь збоку.
3. Опис має підпис-підказку про директивне формулювання.
4. Вкладка Skills у редакторі агента дозволяє прив'язати, відв'язати і
   переставити скіли; порядок зберігається і визначає порядок блоків у промпті.
5. Імпорт `.md` і `.zip` проходить через прев'ю; без підтвердження в БД нічого
   не з'являється; виконувані частини архіву перелічені як пропущені й не
   збережені.
6. Увімкнений прив'язаний скіл видно у трасі прогону окремим блоком і в логах;
   вимкнений — ні.
7. Агент **Test Quality Reviewer** існує з прив'язаними скілами.
8. Контрольний експеримент відтворюється за
   [`skills-control-experiment.md`](skills-control-experiment.md).
