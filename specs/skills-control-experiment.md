# Контрольний експеримент: чи змінюють скіли результат ревʼю

Питання, на яке відповідає експеримент: **скіл справді змінює те, що знаходить
агент, чи це лише зайві токени?** Порядок дій фіксований, щоб два прогони
відрізнялися рівно однією змінною — набором увімкнених скілів.

Спека фічі: [`skills.md`](skills.md).

## Що тут доводиться, а що — ні

| Твердження | Чим доводиться |
|---|---|
| Увімкнений скіл додає у промпт окремий блок; вимкнений — ні | **детерміновано**: `server/test/reviews-skills.it.test.ts` (4 кейси) |
| Порядок блоків = порядок у вкладці Skills | детерміновано, той самий файл |
| Імпортований скіл підписаний як чужий текст | детерміновано, той самий файл |
| Зі скілом агент знаходить те, що без нього пропускає | **емпірично**: прогін нижче; модель стохастична, тож один прогін — ілюстрація, а не доказ |

Не плутати ці два рядки: суворе твердження — про промпт, а не про знахідки.
Знахідки показуємо на демо, промпт — тестами.

## Передумови

1. Стек піднятий (`./scripts/dev.sh`), у Settings → API Keys є ключ провайдера
   агента.
2. У воркспейсі є репозиторій із імпортованими PR (потрібен `GITHUB_TOKEN`).
3. Сид створив агентів і скіли: `Test Quality Reviewer` (3 скіли),
   `General Reviewer` (`pr-quality-rubric`, `api-contract-gate`).

Під кожен експеримент потрібен PR із відповідним дифом — код нижче створює його
за хвилину у власному тестовому репозиторії.

## Експеримент 1 — Test Quality Reviewer

### Диф (happy-path тест і нічого більше)

`src/retry.ts`

```ts
export async function retry<T>(fn: () => Promise<T>, attempts = 3): Promise<T> {
  let lastError: unknown;
  for (let i = 0; i < attempts; i++) {
    try {
      return await fn();
    } catch (err) {
      lastError = err;
      if (i === attempts - 1) break;
      await new Promise((r) => setTimeout(r, 2 ** i * 100));
    }
  }
  throw lastError;
}
```

`src/retry.test.ts`

```ts
import { describe, it, expect } from "vitest";
import { retry } from "./retry";

describe("retry", () => {
  it("works", async () => {
    const result = await retry(async () => 42);
    expect(result).toBe(42);
  });
});
```

Три гілки додано, перевірена одна: повторна спроба після помилки, вичерпання
спроб (кидає останню помилку) і `attempts = 0` (повертає `undefined`… точніше,
кидає `undefined` — саме це й має знайти агент).

### Прогін A — без скілів

1. Agents → Test Quality Reviewer → **Skills**: зняти галочки з усіх трьох.
2. PR → Run review цим агентом.
3. Trace and Logs → **Prompt assembly**: блока `Skills` немає; у логах рядок
   *“No enabled skills linked to this agent”*.
4. Записати: кількість знахідок, їх заголовки, `≈tokens` біля блока `User / diff`.

### Прогін B — зі скілами

1. Та сама вкладка Skills: повернути `test-coverage-rubric`,
   `edge-case-checklist`, `mock-overuse-gate` (порядок саме такий).
2. Re-run на тому самому PR (диф не змінювався).
3. Trace → Prompt assembly: зʼявився блок **Skills**, у ньому три
   `### Skill: …` заголовки в тому ж порядку; біля блока видно `≈N tok` —
   це і є «додані скілом токени».
4. Записати той самий набір чисел.

### Що вважаємо успіхом

Прогін B називає хоча б одну з непокритих гілок (`attempts` вичерпано / нуль
спроб) або межовий вхід, якого немає у A. Якщо B нічого не додав — це теж
результат: він означає, що скіл сформульований надто загально, і його треба
переписати, а не вимкнути.

## Експеримент 2 — API Contract (General Reviewer)

### Диф (зміна сигнатури роуту)

```diff
-app.get('/repos/:id/pulls', { schema: { params: IdParams } }, async (req) => {
-  return service.list(req.params.id);
+app.get('/repos/:id/pulls', { schema: { params: IdParams, querystring: ListQuery } }, async (req) => {
+  // `status` більше не опційний
+  return service.list(req.params.id, req.query.status);
 });
```

`ListQuery`:

```ts
const ListQuery = z.object({ status: z.enum(['open', 'merged', 'closed']) });
```

Ламання: кожен наявний клієнт викликає роут без `status` і після цього дістає
422. Жодної версії, дефолта чи deprecation-вікна в дифі немає.

### Прогін

Той самий сценарій: спершу зняти `api-contract-gate` з General Reviewer,
прогнати, потім повернути і прогнати ще раз. Успіх — у другому прогоні є
знахідка про breaking change із поясненням, який саме виклик перестає працювати.

## Що показувати на відео

1. Вкладку Skills агента: галочки й порядок — **порядок = порядок блоків**.
2. Trace прогону A: блока Skills немає.
3. Trace прогону B: блок Skills, три підписані скіли, `≈N tok` поруч.
4. Список знахідок A vs B.
5. Окремо — довіра: імпортований скіл приходить вимкненим, і вмикаючи його, ви
   свідомо додаєте чужі інструкції у промпт свого агента.

## Чому результат може не відтворитись

- Модель стохастична: той самий промпт дає різні формулювання, іноді різну
  кількість знахідок. Порівнюйте *чи знайдено гілку*, а не текст.
- `grounding` викидає знахідку, чий `file:line` не перетинається з дифом —
  знахідка могла бути і зникнути. Дивіться `grounding` у Stats траси.
- Дешева модель гірше тримає довгий промпт: зі скілами вона може «загубити»
  щось, що бачила без них. Це аргумент за короткі скіли, а не проти скілів.
