## What Doesn't Work

2026-06-30 — On macOS, `fs.realpath('/var/folders/...')` returns `/private/var/folders/...` (because `/var` is a symlink to `/private/var`). Path-guard tests that assert the return value of `assertInsideClone` / `assertInsideCloneForWrite` against `path.join(root, 'subdir/file')` fail with "Expected /var/... Received /private/var/...". Fix: use `await fs.realpath(root)` as the base for the expected path in the assertion. ref: server/src/modules/project-context/path-guard.test.ts:54

2026-06-30 — `import { type Dirent } from 'node:fs/promises'` fails with TS2305/TS2694 "Module 'node:fs/promises' has no exported member 'Dirent'" — even though `readdir({withFileTypes:true})` returns `Dirent[]`. Fix: import `Dirent` from `node:fs` instead: `import { type Dirent } from 'node:fs'`. The `fs/promises` module only re-exports async functions, not types. ref: server/src/modules/project-context/discovery.ts:23

2026-06-22 — Refactoring an inline SSRF guard into a container-wired adapter: the old inline helper (`safeFetchSkillUrl` in skills/routes.ts) had identical logic but was unreachable from other modules. Lifting it to `WebFetchAdapter` + `WebFetchClient` port lets the intent module reuse it via `container.webFetch.fetch()` without re-implementing SSRF guards. The route refactor must remove the unused import (`ValidationError`) or typecheck warns. ref: server/src/modules/skills/routes.ts:1

2026-06-22 — The Edit tool's `old_string`/`new_string` params silently substitute Unicode typographic quotes (curly `'`/`'`) for ASCII single-quote delimiters when the replacement block contains other Unicode characters (e.g. `·` middle-dot, curly apostrophe `'`). In `platform.ts` this produced TS1127 "Invalid character" errors across the entire `FEATURE_MODELS` array. Fix: use a Python byte-level `open(..., 'rb')`/`write` to replace only the target bytes without touching surrounding quote characters. ref: server/src/vendor/shared/contracts/platform.ts:51

2026-06-17 — `selectDistinctOn([agentRuns.prId])` for cost silently returns null when the most recent run errored (`cost_usd = null`). DISTINCT ON picks the newest row regardless of whether the value is null — so a trailing error run zeros out the entire COST column. Fix: use `sql\`sum(${t.agentRuns.costUsd})\`` with `.groupBy(t.agentRuns.prId)` — SQL SUM skips nulls, so error runs don't affect the total. ref: server/src/modules/pulls/routes.ts:122

2026-07-08 — Writing GitHub Actions YAML from a JS/TS template literal is a trap: GHA expression syntax `${{ github.event... }}` starts with the exact same two characters (`${`) that open JS template-literal interpolation. Typing `${{ x }}` literally inside a backtick string makes the TS compiler try to parse `{ x }` as an object-literal expression, which fails to compile (or worse, silently produces the wrong text if `x` happens to be valid JS). Fix used in `workflow.ts`: define every literal GHA expression as a named string constant in `constants.ts` (e.g. `PR_HEAD_SHA_EXPR = '${{ github.event.pull_request.head.sha }}'`) and interpolate the *constant*, never type `${{` directly inside the template literal. The only safe alternative is escaping the leading `$` as `\$`. ref: server/src/modules/ci/workflow.ts:1

2026-07-08 — A test asserting `expect(yamlText).not.toContain('pull_request_target')` can be defeated by your OWN inline YAML comment that mentions the forbidden string for documentation purposes (e.g. "never pull_request_target, which would..."). The comment text is part of the generated file, so the substring match fires on the comment, not a real security violation. Fix: phrase security-invariant comments in generated output without spelling out the exact forbidden token (e.g. "the base-repo-privileged event variant" instead of naming `pull_request_target`) so string-based negative assertions test the real invariant, not prose. ref: server/src/modules/ci/workflow.ts:82

2026-07-08 — `db/rows.ts` explicitly names "ci" as an intended consumer in its own doc comment ("cross-cutting consumers (ci, eval, performance, conformance, compose, hooks, runs, reviews)") — this is the correct import source for `AgentRow`/`SkillRow` in a new module's service, NOT `modules/agents/repository.ts`. Trap: `container.agentsRepo.getById()` returns the raw Drizzle `AgentRow` (camelCase: `systemPrompt`, `ciFailOn`, `provider`, `model`, `strategy`), which is a DIFFERENT shape from the snake_case `Agent` DTO (`system_prompt`, `ci_fail_on`) produced by `toAgentDto()` in `agents/helpers.ts`. A service consuming `AgentRow` directly (e.g. to feed T4's `buildAgentManifestYaml`, whose `AgentManifestSource` param uses snake_case field names) must map field-by-field — do not assume DTO field names apply to the raw row. ref: server/src/db/rows.ts:1

2026-07-08 — Resolving a sibling package's build output from inside a Fastify module (`agent-runner/dist/index.js` from `modules/ci/service.ts`) works identically under both `tsx watch src/server.ts` (dev) and `node dist/server.js` (prod) using `fileURLToPath(new URL('../../../../agent-runner/dist/index.js', import.meta.url))` — because `tsc -p tsconfig.json` mirrors `src/`'s directory depth exactly into `dist/` (`src/modules/ci/service.ts` → `dist/modules/ci/service.js`), the same number of `../` segments reaches the repo root from either location. No env var or `process.cwd()`-based path is needed. ref: server/src/modules/ci/service.ts:1

## Codebase Patterns

2026-06-30 — `assertInsideCloneForWrite` (path-guard.ts) uses `realpath` on the **parent directory** when the target file does not yet exist — this allows creating a brand-new file inside the clone while still blocking a symlinked parent. The key: `fs.realpath(resolved)` throws ENOENT → catch → `realpath(path.dirname(resolved))` instead. `assertInsideClone` (for reads) requires the file to already exist; it will throw ValidationError with the ENOENT code if the file is absent. ref: server/src/modules/project-context/path-guard.ts:52

2026-06-30 — The `assertContained` guard uses `realTarget.startsWith(realRoot + path.sep)` (NOT a bare prefix like `realRoot`). The `path.sep` suffix is mandatory: without it `/clone-root-extra/file` would pass when `realRoot` is `/clone-root`. Both `realRoot` and `realTarget` must be realpath-expanded before comparison or a symlink at any segment can still escape. ref: server/src/modules/project-context/path-guard.ts:115

2026-07-08 — The fork-secret-withholding pattern for the exported GHA workflow (T4, export-to-ci plan): gate the ENTIRE job (not individual steps) with `if: github.event.pull_request.head.repo.fork == false` on the job itself, use the plain `pull_request` trigger (never the base-repo-privileged `*_target` variant), and whitelist-filter any caller-supplied trigger list against a fixed `ALLOWED_PULL_REQUEST_EVENTS` constant before rendering `on:` — never trust the caller's array directly, even though the Zod contract (`CiExportInput.triggers`) already constrains it at the API boundary. This defense-in-depth filtering in the pure generator (`workflow.ts::normalizeTriggers`) means a future caller bug can never smuggle `issue_comment`/`pull_request_review_comment` into a generated workflow. ref: server/src/modules/ci/workflow.ts:1

2026-07-08 — Manifest slugs (`slug.ts`) are intentionally NEVER persisted — `slugify()` is a pure, deterministic function of the display name (decision Q6 in specs/2026-07-08-export-to-ci.md), and collision disambiguation (`disambiguateSlug`) takes the used-slugs set as a plain function argument rather than reading from a DB/repo. This keeps `modules/ci/slug.ts` a zero-dependency pure module; T5 (`service.ts`) is responsible for collecting the "already used" slug set (e.g. from sibling skills/agents in the same export) and passing it in. ref: server/src/modules/ci/slug.ts:1

2026-06-29 — A new module's service must NOT do direct Drizzle queries (`container.db.select()`) — all DB access belongs in a dedicated `repository.ts`. This is an Onion Architecture enforcement: Application layer (service.ts) must not depend on Infrastructure (Drizzle). Pattern: `this.repo = new BlastRepository(container.db)` in the service constructor; all `db.*` calls live in `repository.ts`. Architecture reviewer catches this as a HIGH violation. ref: server/src/modules/blast/service.ts:1

2026-06-29 — Two parallel type hierarchies exist for blast radius data: `server/src/modules/repo-intel/types.ts` has internal types (`BlastChangedSymbol`, `BlastCallerRow`, `BlastResult`) used within repo-intel; `server/src/vendor/shared/contracts/brief.ts` has the HTTP contract types (`BlastChangedSymbol`, `BlastCallerRow`, `BlastRadiusResult`). They are structurally compatible but distinct — the `Blast` prefix on the shared types avoids collision. `BlastService` maps internal → contract before returning. Never merge them; the internal types can evolve independently of the HTTP contract. ref: server/src/vendor/shared/contracts/brief.ts:155

2026-06-29 — MCP tools that hit the API must be registered with the HTTP client injected: `registerGetBlastRadius(server, client, { resolvePullId })`, not `registerGetBlastRadius(server)`. A tool registered without `client`/deps can only be a stub — the moment it needs to call the API it has nothing to call. Our composition root (`mcp-server/src/index.ts`) wires `client` + application-core deps into every non-trivial tool. ref: mcp-server/src/index.ts:63

2026-06-22 — The minimal `Logger` type (`{ info, warn, error, debug }`) for new server modules is NOT exported from `@devdigest/shared` — it lives in `server/src/modules/reviews/run-executor.ts` as `export type Logger`. Import it with `import type { Logger } from '../reviews/run-executor.js'`. ref: server/src/modules/reviews/run-executor.ts:31

2026-06-20 — Layer mapping for Onion Architecture: Domain=`src/vendor/shared/contracts/` (pure TS types, zero framework imports), Application=`modules/*/service.ts` (orchestration, no SQL), Infrastructure=`modules/*/repository.ts` + `src/adapters/` (Drizzle, Octokit, OpenAI SDK), Presentation=`modules/*/routes.ts` (Fastify handlers). To add cross-module data access, add a property to `Container` first, then use it via `this.container.X`. ref: server/src/platform/container.ts:1

2026-06-20 — `getContext(container, req)` is the mandatory first call in every Fastify route handler — it extracts `workspaceId` + `userId` from the auth context. 2026-06-18 — `agent_runs` stores only total `findingsCount` and `blockers` — no per-severity breakdown. To get critical/warning/suggestion counts per run, use: `findings` JOIN `reviews` (on `reviews.id = findings.reviewId`), filter `inArray(t.reviews.runId, runIds)`, group by `(reviews.runId, findings.severity)`. Second query pattern, merge into result map. ref: server/src/modules/reviews/repository/run.repo.ts:51

2026-06-17 — `nullish()` (not `nullable()` or `optional()`) is the convention for optional DTO fields in `platform.ts`. Use `z.number().nullish()` for fields that may be absent from older DB rows — accepts both `null` and `undefined` from Drizzle. ref: server/src/vendor/shared/contracts/platform.ts:157

2026-07-08 — When adding a FK column + composite index/unique-index to an existing `pgTable`, the codebase convention is the object-callback form `(t) => ({ name: index(...).on(t.col) })` (see `pulls.ts`), not the newer array-callback form `(t) => [index(...)]` — both are valid drizzle-kit syntax on this version (`drizzle-orm@0.38.3`), but the object form is what's actually used everywhere else in `src/db/schema/`. ref: server/src/db/schema/pulls.ts:30

2026-07-08 — `agent_runs` has no dedicated `verdict` column, and adding one is a schema change out of scope for a read-path task. `CiRun.verdict` (T6) is instead derived at DTO-mapping time (`CiService.listRuns`) purely from the already-persisted `findingsCount`/`blockers`: `findingsCount === 0 → 'approve'`, else `blockers > 0 → 'request_changes'`, else `'comment'`. This is provably the same predicate reviewer-core's `gateTriggered(findings, failOn)` uses, because `gateTriggered(...) === countBlockers(...) > 0` by construction — so `blockers` (computed once, at ingest time, via the real `countBlockers` call) already encodes the gate decision; no second/duplicate CI-specific verdict rule is needed anywhere. ref: server/src/modules/ci/service.ts:238

2026-07-08 — `CiResultArtifact` (the JSON the agent-runner writes) carries only aggregate severity counts (`critical`/`warning`/`suggestion`), never individual `Finding[]`. To reuse reviewer-core's `countBlockers`/`gateTriggered` (which require `Finding[]`) without forking their logic, ingest synthesizes placeholder findings — one per unit of count, with empty content fields and only `severity` set — then feeds that array through the real functions. This keeps the "same gate computation for CI and local runs" invariant (AC-29) exact rather than approximate. ref: server/src/modules/ci/ingest.ts:136

2026-07-08 — Pull-based CI ingest needs two distinct failure classes, not one: (1) `github.listWorkflowRuns()` throwing (rate-limit/API-down) marks the WHOLE refresh `degraded: true` and writes zero rows for that installation — a transient outage must never fabricate partial data; (2) a failure isolated to one run (`downloadArtifact` throwing, a corrupt zip, `JSON.parse` throwing, or `CiResultArtifact.safeParse` failing) only skips that single run and is NOT degraded — the refresh keeps going and other valid runs in the same installation still ingest. Conflating the two (e.g. treating any per-run failure as "degraded") would make one bad/expired artifact block ingestion of everything else in the same poll. ref: server/src/modules/ci/ingest.ts:45

2026-07-08 — `ncc build src/index.ts -o dist` (agent-runner's bundler) does not always emit a single self-contained `index.js` — dynamic `import()` calls get split into extra chunk files that `index.js` loads relative to its own directory at runtime. Confirmed on this build: `agent-runner/dist/` contains `index.js` + `310.index.js` + `package.json`, not just the entry point. Any export/distribution path that ships an ncc/webpack/esbuild bundle by reading the named entry file alone (`readFileSync('.../dist/index.js')`) will silently omit the chunk files and break at runtime the moment the split-off code path executes. Fix: enumerate and ship the entire `dist/` directory (`readdirSync(dir, { recursive: true })` + `statSync().isFile()` filtering, Node ≥20.1), preserving relative paths. ref: server/src/modules/ci/service.ts:1

## Tool & Library Notes

2026-07-08 — `yaml` (v2.9.0) resolves in `server/node_modules/` and is importable, but it is NOT a declared dependency in `server/package.json` — it's a transitive dependency of `docker-compose` (pulled in by `testcontainers`, a devDependency). Importing it directly from product code (e.g. a manifest serializer) would be a phantom-dependency bug: it could vanish silently if testcontainers/docker-compose ever drop it, and it may be absent entirely from a `pnpm install --prod` tree. Verified via `grep -n "yaml@" server/pnpm-lock.yaml` → only listed under `docker-compose@0.24.8: dependencies: yaml: 2.9.0`. Fix used in T4 (export-to-ci): hand-roll deterministic YAML with double-quoted, JSON-escaped scalars (`JSON.stringify(value).slice(1,-1)` for the body) — this is valid YAML (JSON string escaping is a strict subset of YAML double-quoted scalar escaping) without adding a new declared dependency. ref: server/src/modules/ci/manifest.ts:1

2026-06-30 — When `meta/0010_snapshot.json` is absent, `pnpm db:generate` diffs against snapshot 0009 and re-emits every column added by migration 0010 (e.g. `threat_level`) alongside the genuinely new columns. Fix: manually remove the already-applied column lines from the generated SQL before committing. The `meta/_journal.json` and the new snapshot are still correct — only the `.sql` file needs the spurious lines stripped. ref: server/src/db/migrations/0011_loud_banshee.sql:1

2026-06-17 — `sql` template tag from `drizzle-orm` is NOT included in the common named-export bundle used in this file (`and, desc, eq, inArray`). When adding raw SQL expressions (e.g. `sql\`sum(...)\``), add `sql` to the import explicitly: `import { and, desc, eq, inArray, sql } from 'drizzle-orm'`. Missing it gives a "sql is not defined" runtime error, not a TS error. ref: server/src/modules/pulls/routes.ts:3

2026-06-17 — Drizzle `selectDistinctOn([col])` requires the first `orderBy()` column to match the DISTINCT ON column. For "latest row per group": `.selectDistinctOn([t.agentRuns.prId], {...}).orderBy(t.agentRuns.prId, desc(t.agentRuns.ranAt))`. Without the matching prId in orderBy, Postgres throws "SELECT DISTINCT ON expressions must match initial ORDER BY expressions". ref: server/src/modules/pulls/routes.ts:1

2026-07-08 — No ZIP-reading dependency (`adm-zip`/`unzipper`/`jszip`/`yauzl`) exists in `server/package.json`, and Node's built-in `zlib` only exposes raw deflate primitives (`inflateRawSync`/`deflateRawSync`) — no ZIP *container* parser. To read a GitHub Actions artifact (a plain PKZIP archive) without adding a lockfile dependency, hand-roll a minimal reader: scan backward from EOF for the End-Of-Central-Directory signature `0x06054b50` (search window must extend past a possible trailing zip comment, up to 65535 bytes), walk central-directory entries (signature `0x02014b50`) to find the named entry + its local-header offset, then read the local file header (signature `0x04034b50`) to locate the compressed data, and finally `inflateRawSync()` it if `compressionMethod === 8` (deflate) or copy raw bytes if `=== 0` (stored). Verified round-trip correctness by writing a matching hand-rolled ZIP *writer* in the integration test file and confirming the reader extracts the exact original JSON. ref: server/src/modules/ci/ingest.ts:173

2026-07-08 — Review-gate fix session (export-to-ci F1-F4): `buildExportFiles`'s `workflow_override` handling applies the override to the already-generated `CiFile[]` (mutating the matched `.contents` field after `buildGhaWorkflowFile`/`buildCiConfigFiles` runs) rather than threading it through the generator itself — this keeps `workflow.ts` a pure function of `{triggers, postAs}` with no knowledge of user overrides, and makes the override apply identically on both the `open_pr` and `files` export actions since both paths call the same `buildExportFiles` method before branching. ref: server/src/modules/ci/service.ts:104
