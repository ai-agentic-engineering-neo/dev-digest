# Organize the frontend around features, not file types

Authoritative sources from 2023–2026 converge on one model: **most code lives in feature modules (`features/<x>/`), next to them sits a thin shared layer (`components/ui`, `lib`, `utils`, `config`, `types`), and on top there is a composition layer (in Next.js, `app/` with its routes). Imports flow in one direction only, shared → features → app, and features do not import each other** ([Bulletproof React](https://github.com/alan2207/bulletproof-react/blob/master/docs/project-structure.md), [Feature-Sliced Design](https://feature-sliced.design/docs/get-started/overview), [Robin Wieruch](https://www.robinwieruch.de/react-folder-structure/)). Neither React nor Next.js officially imposes a structure. Next.js explicitly calls itself "unopinionated", offers three equally valid strategies and only asks you to pick one and stick to it ([Next.js Project structure](https://nextjs.org/docs/app/getting-started/project-structure)). So "best practice" here means community consensus plus the official boundary rules (Server/Client Components, `server-only`, data access models). Underneath the model are five independent rules: colocation with promotion upward only after a second consumer appears, business rules in plain TS modules without React, server data in a cache library (`queryOptions`) instead of `useState`, a single typed API client that validates responses at the boundary, and boundaries checked by a linter. For DevDigest (Next.js 15, next-intl v3, TanStack Query, a separate Fastify backend), Next.js recommends the "External HTTP APIs" model with zero trust. As a result, the client needs neither its own DAL over Postgres nor Route Handlers that mirror Fastify. The closest reference implementation is `apps/nextjs-app` from Bulletproof React. Sources openly contradict each other on barrel files, feature vs type folders, what `lib` means, and file naming rules. The skill should present these topics as team decisions, not as truth.

## Three mature references give one model at three levels of scale

**Bulletproof React** is the most frequently cited reference. Its `src/` consists of `app` (routes, providers), `components` (shared), `config` (global configuration, env), `features` ("where most code should live"), `hooks`, `lib` (preconfigured libraries), `stores`, `testing`, `types`, `utils`. A feature contains only those subfolders from the set `api/components/hooks/stores/types/utils` that it actually needs. Imports between features are forbidden, and features are composed at the application level ([Bulletproof React: Project Structure](https://github.com/alan2207/bulletproof-react/blob/master/docs/project-structure.md)). The rule is not just a declaration: ESLint `import/no-restricted-paths` set to `'error'` defines a separate zone per feature and forbids `features → app` and `components/hooks/lib/types/utils → features|app` (same source). Note that the example zones omit `config`, `stores`, `assets` and `testing`, so when copying the config you have to add them by hand.

**Feature-Sliced Design (v2.1)** is a stricter and more detailed version of the same idea. Layers go top to bottom: App → Pages → Widgets → Features → Entities → Shared (the Processes layer is **deprecated**). The rule: a module imports only from layers **strictly below** it. Slices of the same layer cannot see each other, and inside a slice code is split into segments by purpose: `ui`, `api`, `model`, `lib`, `config` ([FSD Overview](https://feature-sliced.design/docs/get-started/overview)). Each slice has a public API: an `index` with explicit re-exports and no `export *`. Cross-imports between entities are allowed only through the `@x` notation and only on the Entities layer ([FSD Public API](https://feature-sliced.design/docs/reference/public-api)). These rules are checked by a dedicated linter, Steiger (`fsd/forbidden-imports`, `fsd/public-api`) ([Steiger](https://github.com/feature-sliced/steiger)).

**Juntao Qiu on martinfowler.com** describes the same principle at the level inside a feature. React should be only the view layer. State and coordination are handled by hooks, business rules live in domain objects in plain TS, and a network gateway acts as an anti-corruption layer over network calls ([Modularizing React Applications](https://martinfowler.com/articles/modularizing-react-apps.html)). The three sources nest into each other: FSD segments `ui/api/model/lib/config` and Bulletproof's feature subfolders (`components/api/hooks/stores/types/utils`) map to Qiu's view / gateway / domain+hooks layers. For the skill this is one model at three levels of scale: application → feature → layer inside a feature.

The mechanism that holds the model together is **colocation and the promotion rule**. Kent C. Dodds puts it as "Place code as close to where it's relevant as possible": tests sit next to the module, styles and state next to the UI, helpers in the consuming file until they are actually reused ([Kent C. Dodds: Colocation](https://kentcdodds.com/blog/colocation)). Wieruch says the same in operational form (updated 2026-05-05): a util, hook or component used by one feature stays in it, and as soon as two or more features need it, it is lifted into shared ([Robin Wieruch](https://www.robinwieruch.de/react-folder-structure/)). Wieruch and Kettmann describe structure as an evolution: single file → folder per component → technical folders → feature folders ([Kettmann / profy.dev](https://dev.to/profydev/screaming-architecture-evolution-of-a-react-folder-structure-4g25)). So type-based grouping is a legitimate starting point for a small app, not a mistake. The legacy React documentation also accepted both approaches, advised keeping nesting within 3–4 levels and not spending "more than five minutes" on the choice ([React legacy FAQ](https://legacy.reactjs.org/docs/faq-structure.html)). The current react.dev has no page on folder structure.

Boundaries are real only when a linter checks them. For Bulletproof's three-layer model `import/no-restricted-paths` is enough: it compares the zone against the resolved path, so `@/` aliases are covered too ([eslint-plugin-import](https://github.com/import-js/eslint-plugin-import/blob/main/docs/rules/no-restricted-paths.md)). For a custom model with element types, `eslint-plugin-boundaries` v7 fits; its main rule is now `boundaries/dependencies`, while `element-types`, `entry-point` and `no-private` are marked deprecated ([jsboundaries.dev rules](https://www.jsboundaries.dev/docs/rules/)). For graph rules and cycles in CI there is `dependency-cruiser` ([dependency-cruiser](https://github.com/sverweij/dependency-cruiser)). To keep shared folders from rotting with dead code, Knip finds unused files and exports ([Knip](https://knip.dev/)).

## App Router: `app/` routes, and the `'use client'` boundary runs along the leaves of the tree

Next.js provides four organization tools. The first is safe colocation: a route becomes public only when the segment has a `page` or `route` file, so other files in `app/` are not routed. The second is private folders `_folder`, which exclude themselves and all subfolders from routing. The docs recommend them to separate UI logic from routing, keep files organized in the editor and avoid conflicts with future conventions. The third is route groups `(group)`, which group routes by section, intent or team without affecting the URL and allow separate layouts. The fourth is the optional `src/`. There are three official strategies: code outside `app/` (`app` "purely for routing purposes"), code in top-level folders inside `app/`, or splitting by feature or route. The names `components` and `lib` have no special meaning to the framework ([Next.js Project structure](https://nextjs.org/docs/app/getting-started/project-structure)). Wieruch advises the opposite of private folders: keep `features/` next to `app/` in `src/` so features can be reused across pages ([Wieruch](https://www.robinwieruch.de/react-folder-structure/)). The compromise is simple: `app/<route>/_components` holds only what belongs to a single route.

FSD on top of App Router requires renaming its own layers to `_app` and `_pages`, keeping Next's `app/` at the root, and making `page.tsx` a thin re-export such as `export { ExamplePage as default, metadata } from '@/_pages/example'`. If server code leaks into the client bundle through a shared `index.ts`, FSD recommends adding `index.server.ts` ([FSD with Next.js](https://feature-sliced.design/docs/guides/tech/with-nextjs)). The idea "the route file is thin, the logic is in the feature" is useful even without FSD.

The most important architectural rule of App Router is the module graph boundary. `'use client'` marks "the module and its transitive dependencies as client code", so everything such a file imports also ends up on the client ([react.dev 'use client'](https://react.dev/reference/rsc/use-client)). Next.js advises putting the directive on interactive leaf files rather than marking large parts of the UI as client. Server Components can be passed into Client Components via `children` or other props (interleaving). Context does not work in Server Components, so a provider is moved into a separate `'use client'` file and rendered "as deep as possible". Third-party components without the directive are re-exported from your own `'use client'` file. `import 'server-only'` breaks the build if the client accidentally imports the module ([Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components)). Props crossing the boundary must be serializable: functions and class instances do not pass, while Server Functions, JSX and Promises do ([react.dev](https://react.dev/reference/rsc/use-client)). Lee Robinson adds the typical mistakes: `"use client"` in every file, context in Server Components, calling your own Route Handlers from Server Components, `redirect()` inside try/catch ([Vercel: Common mistakes](https://vercel.com/blog/common-mistakes-with-the-next-js-app-router-and-how-to-fix-them)).

Since Next.js 16 (2025-10-21) the live docs use new names: `middleware.ts` became `proxy.ts`, synchronous access to `params` and `cookies()` was removed, and `refresh()` and `updateTag()` were added ([Next.js 16](https://nextjs.org/blog/next-16)). The architectural advice did not change between 15 and 16, but a skill for a Next 15 project must flag APIs that exist only in 16. Consider `getServerSideProps`/`getStaticProps`, `pages/api` as the default backend, and URLs like `nextjs.org/docs/13|14/.../colocation` outdated.

## Components are split by responsibility and joined by composition

react.dev gives the basis for decomposition: a component "should ideally only be concerned with one thing", the hierarchy mirrors the data model and the mockup, and a part is extracted into its own component when it grows complex. The example is a table header that becomes `ProductTableHeader` as soon as it gets sorting ([Thinking in React](https://react.dev/learn/thinking-in-react)). There is one hard rule: **never declare a component inside another component**, because it is "very slow and causes bugs". Several small related components in one file are fine until the file gets crowded ([Your First Component](https://react.dev/learn/your-first-component)). "One component per file" is a convention, not a React rule. Dodds advises deleting `no-multi-comp` "and all rules like it" ([Dodds: Colocation](https://kentcdodds.com/blog/colocation)), and Comeau confirms it is "not required" ([Comeau](https://www.joshwcomeau.com/react/file-structure/)). Rendering must be pure, side effects live in event handlers, and `useEffect` remains "your last resort" ([Keeping Components Pure](https://react.dev/learn/keeping-components-pure)). TkDodo advises expressing mutually exclusive states (loading, error, empty, data) as flat early returns with a shared `Layout` via `children`. A component that keeps growing conditionals is most likely a wrong abstraction ([TkDodo: Component Composition](https://tkdodo.eu/blog/component-composition-is-great-btw)).

The presentational vs container split (Abramov, 2015) is **outdated**. In a 2019 note the author himself writes that his views have changed and that hooks achieve the same without an "arbitrary division". The Medium original cannot be fetched directly, so the wording is known from a reproduction on [LogRocket](https://blog.logrocket.com/how-to-convert-your-existing-redux-containers-to-hooks), and it should be checked against the original before quoting verbatim. patterns.dev separately confirms that "Modern React strongly favors Hooks over container components" ([patterns.dev](https://www.patterns.dev/react/presentational-container-pattern/)). The modern equivalent is the headless component: a hook such as `useDropdown` is responsible "solely for logic and state management", and the UI only reacts to props. The approach pays off when the same behavior is needed with different looks. Overused, it hurts readability, so for typical cases mature libraries (React Aria, Headless UI, TanStack Table) are the better choice ([Qiu: Headless Component](https://martinfowler.com/articles/headless-component.html)). In Next.js, part of the "container" role is taken over by a Server Component that loads data. No primary source states this framing directly, so for the skill it is an inference, not a quote.

The order for choosing a composition tool is as follows. First, explicit props. Next, `children` and slot props ("a 'hole'" for arbitrary JSX). If `posts` passes through a `<Layout>` that does not use it, then "you forgot to extract some components". Context is reserved for theme, current user, routing and the reducer+context pairing ([Passing Props](https://react.dev/learn/passing-props-to-a-component); [Passing Data Deeply with Context](https://react.dev/learn/passing-data-deeply-with-context)). Abramov stresses that "move state down" and "lift content up" primarily make the data flow clearer, and the performance gain is just "a cherry on top" ([Before You memo()](https://overreacted.io/before-you-memo/)). Multi-part widgets are a fit for compound components with shared state via context. A part's hook throws if it is rendered outside its parent ([Dodds: Compound Components](https://kentcdodds.com/blog/compound-components-with-react-hooks)). The `cloneElement` variant breaks as soon as a part is wrapped in another element ([patterns.dev Compound](https://www.patterns.dev/react/compound-pattern/)). For element polymorphism the main pattern is Radix `asChild`. Your own component must then pass through all props and the ref, otherwise "it will break" ([Radix Composition](https://www.radix-ui.com/primitives/docs/guides/composition)). Excessive `{...props}` in application components signals missing decomposition via `children` ([Passing Props](https://react.dev/learn/passing-props-to-a-component)). Fernando Rojo's thesis that a boolean prop selecting a different subtree is a reason for composition is known only from secondary summaries of the talk ([summary](https://youtubesummary.com/summary/4KvbVq3Eg5w)). Vercel packaged the same rule as the agent skill `vercel-composition-patterns` ([skills.sh](https://skills.sh/vercel-labs/agent-skills/vercel-composition-patterns)). The official counterpart is react.dev's rule to replace contradictory boolean state variables (`isSending` + `isSent`) with a single `status` union ([Choosing the State Structure](https://react.dev/learn/choosing-the-state-structure)). For props this is an analogy, not a direct requirement.

Where components live: generic UI without domain knowledge (Button, Dialog, Radix wrappers) goes to the shared `components/ui`. Domain-aware components go to `features/<x>/components`. Pages only compose features and are responsible for data loading and layout ([Bulletproof React](https://github.com/alan2207/bulletproof-react/blob/master/docs/project-structure.md)). A component is lifted into shared only when a second feature needs it, and its domain logic is stripped out at that point. Inside the folder of a complex component, Comeau keeps `FileViewer.tsx`, private subcomponents, `FileViewer.helpers.ts`, `.types.ts`, `.constants.ts` and specific hooks. In App Router, `export *` in `index.ts` caused a duplicate `default` error for him, so he exports explicitly ([Comeau](https://www.joshwcomeau.com/react/file-structure/)).

## Logic, state and the API layer have three separate homes

**Business rules** live in plain TypeScript modules without React imports. Hooks serve as thin glue to state and effects, and components render and forward events. Qiu moves fetching, data transformation, default values and conditional rules out of components and `useEffect` into domain objects and a network gateway. He replaces scattered conditions like `countryCode === "JP"` with a Strategy interface passed in via props ([Qiu](https://martinfowler.com/articles/modularizing-react-apps.html)). Bespoyasov describes a full clean/hexagonal scheme (domain → application/use cases with ports → adapters, where React is a driving adapter) and honestly lists its cost: design time, verbosity on small projects, harder onboarding. He considers only two rules mandatory: a separated domain and dependencies pointing inward ([Clean Architecture on Frontend](https://bespoyasov.me/blog/clean-architecture-on-frontend/), 2021). Kettmann proposes a pragmatic form: a use-case function with a `dependencies` parameter, wrapped by a hook. His main caveat is **do not extract a use case for a simple API request** ([Kettmann, Part 6](https://profy.dev/article/react-architecture-business-logic-and-dependency-injection)). The main benefit all these sources name is testability: a domain function is tested with plain vitest without rendering or network mocks.

**Custom hooks** share stateful logic, not the state itself. Every hook call is independent, so to share state you lift it up. The `use` prefix is allowed only for functions that call at least one hook. A hook wrapping a single `useState` is usually unnecessary, and "lifecycle" hooks such as `useMount` and `useEffectOnce` hide dependencies from the linter ([Reusing Logic with Custom Hooks](https://react.dev/learn/reusing-logic-with-custom-hooks)).

**Server state** is a cache owned by the server. It is not copied into `useState`, because background updates then stop reaching the UI ([TkDodo: Practical React Query](https://tkdodo.eu/blog/practical-react-query)). Dodds distinguishes server cache from UI state ([Application State Management](https://kentcdodds.com/blog/application-state-management-with-react)), and Bulletproof also uses a cache library rather than Redux for server data ([Bulletproof: State Management](https://github.com/alan2207/bulletproof-react/blob/master/docs/state-management.md)). The advice here has changed over time. In 2020–2022 the recommendation was to wrap every query in a hook and keep separate key factories ([Effective React Query Keys](https://tkdodo.eu/blog/effective-react-query-keys)). Since 2024 TkDodo writes: "Separating QueryKey from QueryFunction was a mistake". The unit of reuse is now a `queryOptions` factory, and he calls a hook that merely wraps `useQuery` "a bit pointless" ([The Query Options API](https://tkdodo.eu/blog/the-query-options-api)). In a 2026-02-23 article he clarifies: shared options should be non-configurable (key + fn), while `staleTime`, `select` and `throwOnError` are set at the call site ([Creating Query Abstractions](https://tkdodo.eu/blog/creating-query-abstractions)). The official TanStack documentation supports this approach ([TanStack Query Options](https://tanstack.com/query/latest/docs/framework/react/guides/query-options)). Keys are built from general to specific (`['todos','list',{filters}]`) and colocated in the feature, not in a global keys file ([Effective React Query Keys](https://tkdodo.eu/blog/effective-react-query-keys)).

**The API layer** has one configured client (`src/lib/api-client.ts`) and requests declared outside components. Each declaration contains types and a schema, a fetcher using the shared client, and a hook or query options, and it lives in the feature, e.g. `features/discussions/api/get-discussions.ts`. If many requests are shared by several features, they move to a top-level `api/` ([Bulletproof: API Layer](https://github.com/alan2207/bulletproof-react/blob/master/docs/api-layer.md)). Type the fetch function, not the hook: a generic only on the return value (`axios.get<Todo>`) is effectively a disguised type assertion. Parse the Zod schema with `parse` inside `queryFn`, so invalid data puts the query into a normal `error` state ([TkDodo: Type-safe React Query](https://tkdodo.eu/blog/type-safe-react-query)). The DTO stays inside the API layer: a function like `dtoToUser()` turns it into a domain type, so components never see the raw shape of the backend response. If the response already fits the UI, the mapping can be skipped ([Kettmann: Domain Entities & DTOs](https://dev.to/jkettmann/path-to-a-cleaner-react-architecture-domain-entities-dtos-3ja0)). The resulting pipeline: client → fetcher (Zod parse → DTO mapping) → `queryOptions` → component.

**Global client state** is the last resort. The order is: local state, then lifted to the nearest common parent, then composition, then context when prop drilling actually gets in the way, with a separate context per concern ([Dodds](https://kentcdodds.com/blog/application-state-management-with-react); [State Colocation](https://kentcdodds.com/blog/state-colocation-will-make-your-react-app-faster)). State derived from other data is not stored but computed during render. It is reset with `key`, not with an Effect ([You Might Not Need an Effect](https://react.dev/learn/you-might-not-need-an-effect)). The Redux Style Guide and TkDodo on Zustand state one principle: transition logic lives in reducers or the store, actions model events rather than setters, only custom hooks are exposed, and several small stores are better than one global store ([Redux Style Guide](https://redux.js.org/style-guide/); [Working with Zustand](https://tkdodo.eu/blog/working-with-zustand)). URL state belongs to the router ([Bulletproof: State Management](https://github.com/alan2207/bulletproof-react/blob/master/docs/state-management.md)). Form state lives locally in a form library with a validation schema, not in Redux ([Redux Style Guide](https://redux.js.org/style-guide/)). Server data for a form is only the `defaultValues` of a child form component. After a mutation, the query is invalidated and the form is reset ([React Query and Forms](https://tkdodo.eu/blog/react-query-and-forms)).

## Constants, utilities and types go at the lowest level that covers all their consumers

For **constants** there is a hierarchy: file module scope < component folder < feature < global `config`. react.dev advises moving objects and functions that do not depend on props and state outside the component, because then they are not reactive ([Removing Effect Dependencies](https://react.dev/learn/removing-effect-dependencies)). At the same time, module top-level code runs at import time, so whole-app initialization belongs in the entry point ([You Might Not Need an Effect](https://react.dev/learn/you-might-not-need-an-effect)). Bulletproof puts global configuration in `src/config`, FSD in the `shared/config` segment, with routes as a `routes` segment ([FSD Layers](https://feature-sliced.design/docs/reference/layers)). Comeau uses `src/constants.ts` and `Widget.constants.ts` ([Comeau](https://www.joshwcomeau.com/react/file-structure/)). The Google TS Style Guide allows `CONSTANT_CASE` only for module-level symbols and enum values ([Google TS Style Guide](https://google.github.io/styleguide/tsguide.html)).

**Environment variables** are a special case of constants, and all sources agree on a single schema-validated module that fails fast on error. Bulletproof's `src/config/env.ts` parses env with Zod `safeParse`, throws an error listing the invalid variables and exports a single `env` object ([Bulletproof env.ts](https://github.com/alan2207/bulletproof-react/blob/master/apps/react-vite/src/config/env.ts)). T3 Env proposes `src/env.ts` with `createEnv({ server, client, runtimeEnv })`. It is worth splitting it into `env/server.ts` and `env/client.ts`, otherwise server variable schemas end up in the client bundle. Build-time validation is enabled by importing the env file in `next.config` ([T3 Env: Next.js](https://env.t3.gg/docs/nextjs)). Next.js keeps env server-only by default. Variables prefixed with `NEXT_PUBLIC_` are inlined into the bundle at `next build`, while dynamic access `process.env[name]` is not inlined. `.env*` files live in the project root even when the code is in `src/` ([Next.js Environment Variables](https://nextjs.org/docs/app/guides/environment-variables)).

The terms **utils, helpers and lib** mean different things in different sources, and the skill has to pick one meaning. In Bulletproof, `lib` means "reusable libraries preconfigured for the application" (API client, query client), and `utils` means "shared utility functions", with each feature allowed its own `utils` ([Bulletproof](https://github.com/alan2207/bulletproof-react/blob/master/docs/project-structure.md)). In FSD, `lib` is internal libraries with a single area of responsibility, and the docs say outright that the folder "should not be treated as helpers or utilities", because such folders "often turn into a dump". Segment names should describe purpose, not essence: FSD considers `components`, `hooks` and `types` bad names ([FSD Layers](https://feature-sliced.design/docs/reference/layers); [FSD Slices and segments](https://feature-sliced.design/docs/reference/slices-segments)). Comeau keeps generic functions he carries between projects in `utils`, and project-specific ones in `helpers` (`category.helpers.ts`) ([Comeau](https://www.joshwcomeau.com/react/file-structure/)). Google forbids container classes with static methods used for namespacing, so no `class Utils { static … }` ([Google TS Style Guide](https://google.github.io/styleguide/tsguide.html)). The synthesis for the skill: `lib/` holds configured instances of external libraries, `utils/` holds pure domain-neutral functions, one file per topic, no single `utils.ts` dumping ground, and domain logic stays in its feature.

For **types** there are Matt Pocock's three rules: a type used in one place lives in the same file. A type used in several places moves to a shared location (`*.types.ts`). A type needed by several packages of a monorepo moves to a shared package ([Total TypeScript](https://www.totaltypescript.com/where-to-put-your-types-in-application-code)). `.d.ts` files are for describing JavaScript and global augmentations, not for application types. This is known only from a search snippet; the page was not fetched in full ([Total TypeScript workshop](https://www.totaltypescript.com/workshops/typescript-pro-essentials/types-you-don't-control/should-you-use-declaration-files-to-store-your-types)). Bulletproof combines `src/types` for shared types with `features/x/types`, while FSD keeps types by purpose: schemas in `model`, data types and mappers in `api` ([FSD Slices and segments](https://feature-sliced.design/docs/reference/slices-segments)). Google recommends `import type` for imports needed only as types ([Google TS Style Guide](https://google.github.io/styleguide/tsguide.html)). When a type describes network data, the Zod schema is the source of truth and the type is inferred via `z.infer`. The Zod documentation was not fetched during the research, so the README should link to https://zod.dev here.

There is no common standard for **naming**. Bulletproof requires kebab-case for all `.ts/.tsx` files and folders via `eslint-plugin-check-file` and configures the `@/*` alias ([Bulletproof: Project Standards](https://github.com/alan2207/bulletproof-react/blob/master/docs/project-standards.md); [eslint-plugin-check-file](https://github.com/dukeluo/eslint-plugin-check-file)). Comeau names component files in PascalCase and the rest in kebab-case (`use-boop.js`) and says the specific convention "doesn't really matter" as long as there is one ([Comeau](https://www.joshwcomeau.com/react/file-structure/)). Google insists on snake_case files and named exports only ([Google TS Style Guide](https://google.github.io/styleguide/tsguide.html)). In App Router a "named exports only" rule has to make an exception for `page.tsx` and `layout.tsx`, which require a default export. This is an inference, not a quote from a source.

| One component per file | The "file = component" convention is widespread | "Not required": [react.dev](https://react.dev/learn/your-first-component), [Dodds](https://kentcdodds.com/blog/colocation), [Comeau](https://www.joshwcomeau.com/react/file-structure/) | Allow small private subcomponents in one file, don't enable `no-multi-comp` |
| Meaning of `lib` | Preconfigured third-party libraries: [Bulletproof](https://github.com/alan2207/bulletproof-react/blob/master/docs/project-structure.md) | Internal focused libraries, "not helpers": [FSD Layers](https://feature-sliced.design/docs/reference/layers) | Pick Bulletproof's definition, as it is closer to the current `client/src/lib` |
| `types` folder | `src/types` + `features/x/types`: [Bulletproof](https://github.com/alan2207/bulletproof-react/blob/master/docs/project-structure.md) | `types` is a bad segment name, types live in `model`/`api`: [FSD](https://feature-sliced.design/docs/reference/slices-segments) | Colocate per [Pocock](https://www.totaltypescript.com/where-to-put-your-types-in-application-code)'s rules, shared folder only for truly shared types |
| A hook per query | Wrap `useQuery` in a hook: [Practical React Query](https://tkdodo.eu/blog/practical-react-query) (2020) | `queryOptions` factories, a hook only when it adds logic: [TkDodo 2024](https://tkdodo.eu/blog/the-query-options-api), [2026](https://tkdodo.eu/blog/creating-query-abstractions), [TanStack](https://tanstack.com/query/latest/docs/framework/react/guides/query-options) | The new position. Cite the old one only as history |
| File naming | kebab-case everywhere: [Bulletproof](https://github.com/alan2207/bulletproof-react/blob/master/docs/project-standards.md) | PascalCase for components: [Comeau](https://www.joshwcomeau.com/react/file-structure/); snake_case: [Google](https://google.github.io/styleguide/tsguide.html) | Record the client's current convention and enforce it with `check-file` |
| Private folders in `app/` | `_components`, `_lib` in segments: [Next.js](https://nextjs.org/docs/app/getting-started/project-structure) | Features outside `app/`, no private folders: [Wieruch](https://www.robinwieruch.de/react-folder-structure/) | `_components` only for single-route code, everything reusable in `features/` or `components/` |
| Clean architecture | Full layers with ports and DI: [Bespoyasov](https://bespoyasov.me/blog/clean-architecture-on-frontend/) | No use case for a simple request: [Kettmann](https://profy.dev/article/react-architecture-business-logic-and-dependency-injection) | Only "domain without React" and the dependency direction are mandatory. A use case only when there are real rules |

Setting aside outdated advice, none of these contradictions concern code correctness. They are all about the cost of discipline. So the skill should record a concrete team decision, name the source of each position and back each rule with a linter, rather than re-argue the dispute.

## For DevDigest on Next 15 with a separate Fastify, part of the advice does not apply

Next.js describes three data access models: an HTTP API for existing organizations with a separate backend, a Data Access Layer for new full-stack projects, and component-level access for prototypes. The official requirement is "choosing one data fetching approach and avoiding mixing them" ([Data Security guide](https://nextjs.org/docs/app/guides/data-security)). Markbåge adds that exceptions then "pop out as suspicious" ([Security blog](https://nextjs.org/blog/security-nextjs-server-components-actions)). DevDigest clearly falls into the first model, because Fastify on :3001 owns the DB. Several conclusions follow. The advice about a DAL with `server-only` and DB access does not apply to the client, and the Next side should not know about Postgres. Zero trust applies: Server Components are not treated as a trusted network, and `params` and `searchParams` are validated as untrusted input. A Client Component should not receive "more data than the minimal data it needs", so a broad prop such as `user: User` is a reason for a review comment (same source).

In this model Route Handlers are only a fallback. Next.js says outright that its backend capabilities are "not a full backend replacement". For plain proxying to another backend use `rewrites`, and use a Route Handler only when you need to validate the request, inject server-side credentials or transform the response, with an endpoint allow-list. For streaming only rewrites work ([Backend for Frontend guide](https://nextjs.org/docs/app/guides/backend-for-frontend)). This matters for JobRunner SSE events. Server Components do not call their own Route Handlers, because it is an extra HTTP hop, and for prerendered pages such a call breaks the build (same source). For DevDigest, Server Actions would be an extra BFF hop (action → Fastify). They are justified only for forms with progressive enhancement or for `revalidatePath`. They are not suitable for reading data at all, because they run sequentially ([Mutating Data](https://nextjs.org/docs/app/getting-started/mutating-data)). Every action must be treated as a public POST endpoint with authentication, authorization and argument validation (same source; [Security blog](https://nextjs.org/blog/security-nextjs-server-components-actions)). No source forbids mutations going from the client through TanStack Query straight to Fastify, but none explicitly endorses it either. This is an inference.

The closest working reference is `apps/nextjs-app` from Bulletproof React. There `src/lib/api-client.ts` implements a single `fetchApi` that forwards cookies on the server, `src/lib/react-query.ts` holds the shared configuration, and each `features/<f>/api/<verb-noun>.ts` exports a fetcher, `…QueryOptions` and a hook. Pages call `prefetchQuery` and render `<HydrationBoundary>` around the route's `_components/` client ([bulletproof-react apps/nextjs-app](https://github.com/alan2207/bulletproof-react/tree/master/apps/nextjs-app)). Caveat: that app is on `next ^14.2.5` with synchronous `searchParams`, so for Next 15 the code must be rewritten to async `params` and `searchParams`. The `typeof window` check in the client is better replaced with two modules: a server fetch with `import 'server-only'` and a browser one. This is an inference from the `server-only` rules ([Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components)). A comparison of "SSR prefetch + hydration" vs "fetch in a Server Component + props" for a separate backend is not officially documented anywhere. TanStack's Advanced SSR guide was not read during the research, and this remains an open question.

The actual `client/src` already combines two official strategies: route-level `app/_components`, `app/agents/_components`, `app/onboarding/_components` (strategy 3) and shared `components/`, `lib/`, `lib/hooks` (strategy 1). Next.js considers both acceptable ([Project structure](https://nextjs.org/docs/app/getting-started/project-structure)). There is no `features/` layer yet, and `components/diff-viewer` or `components/run-cost-badge` are in fact domain components in a space meant for shared ones. The skill should state the rule: what belongs to a single route lives in `app/<route>/_components`. Domain code used by several routes lives in `features/<x>/{api,components,hooks,utils}`. `components/` keeps generic UI. Imports are restricted via `import/no-restricted-paths`. `vendor/ui` corresponds in content to the FSD `shared/ui` layer.

Three more deviations from the general advice should be written down explicitly in the README. First: the Zod contracts are copied into `client/src/vendor/shared` and `server/src/vendor/shared`, and the copies have already diverged. This is a deliberate deviation from Pocock's third rule (a shared package for types used by several packages) ([Total TypeScript](https://www.totaltypescript.com/where-to-put-your-types-in-application-code)), so the skill must require changing both copies together. The Fastify response is parsed with the Zod schema from `vendor/shared` in the fetcher, as [TkDodo](https://tkdodo.eu/blog/type-safe-react-query) advises. Second: next-intl. The next-intl.dev docs describe v4 on Next 16 with `proxy.ts` and `next/root-params` ([next-intl routing setup](https://next-intl.dev/docs/routing/setup)), while DevDigest runs next-intl ^3.26 on Next 15. So the applicable guidance is: `messages/<locale>.json` at the root, config in `src/i18n/request.ts`, `NextIntlClientProvider` in the layout, `getTranslations` in Server Components and namespaces by the top-level JSON keys ([next-intl App Router](https://next-intl.dev/docs/getting-started/app-router)). Any examples using `proxy.ts` must be marked "v4/Next 16 only". next-intl gives no official advice on whether to split messages by feature. Third: Next.js 16 renamed `middleware.ts`, so examples from the current docs cannot be trusted without checking the version ([Next.js 16](https://nextjs.org/blog/next-16)).

## Conclusion

The main result of the research: the question "where does code live" in React and Next.js is no longer a matter of taste, even though no framework officially answers it. The official documents set hard runtime boundaries: the `'use client'` boundary, `server-only`, a single data access model and zero trust toward input. On top of them the community has produced one structural model: feature modules, colocation with upward promotion, and unidirectional imports. The remaining disputes (barrel files, feature vs type, kebab-case vs PascalCase, the meaning of `lib`) are about the cost of discipline, not correctness. So a useful skill records one team decision for each and backs every rule with a linter. Without a linter, none of these boundaries will survive the first deadline.

For DevDigest the greatest practical value lies in what must deliberately **not** be carried over from popular advice. A separate Fastify makes a DAL, mirroring Route Handlers and Server Actions for reads unnecessary. The closest reference (Bulletproof `nextjs-app`) has to be ported from Next 14 to 15, and the current Next.js and next-intl docs already describe a world one major version ahead of the one the client runs in. So the skill must tie every piece of advice to the installed version. The open choice is between SSR prefetch with hydration and fetching in a Server Component for a separate backend. It should be settled through an ADR after studying TanStack's Advanced SSR guide, not through the skill.
