# План скіла `pr-self-review`

Статус: **реалізовано** 2026-09-21 — `.claude/skills/pr-self-review/` + хук у
`.claude/settings.json`. Документ лишається як опис задуму; ухвалені рішення — у § 13.

## 1. Мета

Локальна самоперевірка змін **перед** відкриттям PR: зібрати весь відкритий diff,
визначити, які з наявних скілів проєкту стосуються саме цих файлів, прогнати кожен
релевантний скіл по його частині diff-а і винести вердикт. Хоча б один підтверджений
**CRITICAL** → PR відкривати не можна, і `gh pr create` блокується механічно, а не
проханням.

Це dogfooding: DevDigest рев'ює чужі PR-и, а цей скіл тим самим підходом рев'ює власні
зміни до того, як вони стануть PR-ом.

## 2. Не-цілі

- Не замінює `/code-review` і не дублює його: той шукає баги в дифі взагалі, цей
  перевіряє відповідність **конвенціям проєкту**, закодованим у `.claude/skills/`.
- Не запускає тести. Глобальне правило користувача забороняє запуск тестових наборів
  без явного дозволу — скіл робить тільки статичні перевірки (`typecheck`) і читання коду.
- Не робить жодних git-мутацій: не комітить, не пушить, не створює PR. Він лише
  дозволяє або забороняє це зробити користувачеві.
- Не рев'ює історію гілки по комітах — одиниця аналізу це підсумковий diff.

## 3. Тригери

| Спосіб | Як | Що відбувається |
|---|---|---|
| Вручну | `/pr-self-review` (skill `user-invocable`), опційно `--base <ref>`, `--scope working\|branch\|all` | повний прогін і звіт |
| Перед відкриттям PR | `PreToolUse`-хук на `Bash`, matcher `gh pr create` | якщо свіжого вердикту немає або він `blocked` → `exit 2`, виклик не виконується |

Хук **не запускає** скіл сам (хук — це шел-скрипт, він не має моделі). Він перевіряє
артефакт останнього прогону і зупиняє відкриття PR, повертаючи в stderr інструкцію
«запусти `/pr-self-review`». Це єдиний легальний спосіб зробити скіл «автоматичним»:
глобальне правило користувача забороняє самовільний запуск скілів за контекстом.

Вердикт вважається свіжим, якщо в ньому `head_sha` дорівнює поточному `git rev-parse HEAD`
**і** `dirty_hash` дорівнює хешу поточного `git status --porcelain` + `git diff`. Будь-яка
зміна у файлах після прогону робить вердикт протухлим.

## 4. Що таке «всі відкриті зміни»

За замовчуванням `--scope branch`, тобто об'єднання трьох джерел:

1. `git diff --merge-base <base> HEAD` — закомічене в гілці відносно бази;
2. `git diff HEAD` — незакомічене (staged + unstaged);
3. `git ls-files --others --exclude-standard` — нові неігноровані файли.

База визначається так: аргумент `--base` → інакше upstream гілки
(`git rev-parse --abbrev-ref @{u}`) → інакше `origin/main`. Якщо база не резолвиться —
скіл зупиняється і питає, а не вгадує.

Виключається зі скоупу: лок-файли, `server/clones/**`, `docs/design/**`, бінарники,
файли > 1500 змінених рядків (позначаються як «не перевірено» в звіті, а не мовчки
ігноруються).

## 5. Маршрутизація diff → скіли

Ядро скіла. Для кожного зміненого файлу обчислюється набір скілів; далі — об'єднання,
і скіл із порожнім набором файлів не запускається взагалі.

| Патерн шляху | Скіли |
|---|---|
| `client/src/app/**/{page,layout,route,loading,error,template}.tsx\|ts`, Server Actions | `next-best-practices`, `react-best-practices`, `frontend-ui-architecture` |
| `client/src/**/*.tsx` (крім тестів) | `react-best-practices`, `frontend-ui-architecture` |
| `client/src/**/*.test.tsx\|ts` | `react-testing-library` |
| новий/переміщений файл у `client/src/**` | `frontend-ui-architecture` (розміщення, межі імпортів) |
| `server/src/modules/*/routes.ts`, `server/src/platform/{sse,jobs}.ts` | `fastify-best-practices`, `onion-architecture`, `security` |
| `server/src/modules/*/{service,repository}.ts`, `server/src/adapters/**`, `platform/container.ts` | `onion-architecture`, `drizzle-orm-patterns` (для `repository.ts`) |
| `server/src/db/schema.ts`, `server/src/db/migrations/**` | `drizzle-orm-patterns`, `postgresql-table-design` |
| `*/vendor/shared/contracts/**` | `zod`, `onion-architecture` + перевірка дублю (§6, крок 2) |
| `reviewer-core/src/**` | `onion-architecture` (чистота домену), `typescript-expert`, `zod` |
| `e2e/**` | конвенції `e2e/CLAUDE.md` (скіла немає) |
| `.github/workflows/**`, `scripts/**`, `.claude/**`, кореневі `*.md` | тільки конвенції репозиторію |

Поверх шляхів — два контентні тригери, бо шлях їх не ловить:

- `security` додається до будь-якого файлу, у дифі якого з'являється робота з вводом
  користувача, токенами/секретами, `fetch`/`exec`/`child_process`, заголовками,
  `dangerouslySetInnerHTML`, або нова публічна ручка;
- `typescript-expert` додається, коли в дифі є `any`, `as ` каст, нові дженерики,
  умовні/мапнуті типи або зміна `tsconfig`.

**Завжди-увімкнена смуга** (не скіл, а `rules/repo-conventions.md` всередині скіла):
іменування з `CLAUDE.md` § Naming conventions, дві копії `vendor/shared`, заборона
ручного редагування лок-файлів, `*.it.test.ts` для DB-тестів, таймстемп міграції =
сьогоднішня дата, заборона зайвих коментарів у коді.

Маршрутну таблицю тримаємо в окремому файлі `rules/routing.md` — вона змінюється
щоразу, коли в `.claude/skills/README.md` з'являється новий рядок, і має звірятися з
ним (див. критерії приймання).

## 6. Пайплайн прогону

0. **Пре-фліт.** Резолв бази, збір diff-а, `git status`. Якщо змін немає — вихід зі
   звітом «нічого перевіряти», вердикт не пишеться.
1. **Маршрутизація.** Побудувати `{скіл → список файлів}` за §5 і показати цю карту
   користувачеві **до** аналізу: це єдиний доказ, що покриття обране, а не вигадане.
2. **Дешеві детерміновані перевірки** (без моделі, вони ж — найчастіші CRITICAL):
   - `pnpm typecheck` у кожному зачепленому пакеті (`client`, `server`) і `npm run typecheck`
     у `reviewer-core`;
   - контракт змінено в одній копії `vendor/shared`, а не в обох;
   - у дифі з'явився секрет/токен (патерни ключів + `.env` поза `.env.example`);
   - деструктивна міграція (`DROP TABLE`/`DROP COLUMN`) або таймстемп міграції не сьогоднішній;
   - руками змінений `pnpm-lock.yaml` / `package-lock.json` без зміни `package.json`.
3. **Аналіз по скілах.** Один підагент на скіл (паралельно, до 4 одночасно), кожному —
   тільки його файли, його `SKILL.md` і формат виводу з §7. Підагент не має права
   редагувати файли: режим read-only.
4. **Верифікація.** Кожен кандидат у CRITICAL перевіряється другим проходом: відкрити
   файл, підтвердити, що патерн реально там, і сформулювати сценарій відмови. Не
   підтверджено → знижується до WARNING. Це прямий аналог того, що робить `reviewer-core`
   зі своїм grounding-гейтом.
5. **Звіт і вердикт.** Дедуплікація (один і той самий рядок від двох скілів = одна
   знахідка з двома джерелами), сортування за severity, запис артефакту, підсумок.

## 7. Severity і критерій блокування

Використовуємо власний enum проєкту — `Severity` з
`server/src/vendor/shared/contracts/findings.ts`: `CRITICAL` · `WARNING` · `SUGGESTION`.
Жодної нової шкали; скіли з власними шкалами мапляться (`react-best-practices`:
CRITICAL→CRITICAL, HIGH→WARNING, MEDIUM→SUGGESTION; `security`: HIGH confidence→CRITICAL,
MEDIUM→WARNING, LOW→не репортиться).

**CRITICAL ставиться лише тоді, коли виконані всі три умови:** є `file:line`, є
конкретний сценарій відмови (вхід/стан → неправильний результат, падіння, витік або
зламана збірка), і знахідку підтвердив крок 4. Інакше — WARNING. Стиль, «краще було б»,
теоретичні ризики — ніколи не CRITICAL.

Типові справжні CRITICAL для цього репозиторію: зламаний typecheck; контракт у одній
копії `vendor/shared`; секрет у дифі; новий роут без валідації Zod або без перевірки
доступу; `routes.ts`, що імпортує Drizzle (порушення dependency rule); деструктивна
міграція; мутація стану React, яка ламає рендер.

Вердикт: `blocked = (critical_count > 0)`. Обхід — тільки явним розпорядженням
користувача (`/pr-self-review --force` або `PR_SELF_REVIEW_OVERRIDE=1`), і факт обходу
пишеться в артефакт.

## 8. Артефакти і формат звіту

`.claude/pr-self-review/last-run.json` (git-ignored):

```json
{
  "generated_at": "2026-09-21T22:40:00Z",
  "base": "origin/main", "head_sha": "…", "dirty_hash": "…",
  "files": 41, "skills_run": ["react-best-practices", "onion-architecture"],
  "counts": { "CRITICAL": 1, "WARNING": 6, "SUGGESTION": 12 },
  "blocked": true, "override": false,
  "findings": [{ "severity": "CRITICAL", "file": "…", "line": 88,
                 "skill": "onion-architecture", "title": "…", "failure": "…", "fix": "…" }]
}
```

У чат — короткий звіт українською: рядок вердикту (`BLOCKED: 1 CRITICAL` / `OK`),
карта «скіл → скільки файлів», далі знахідки згруповані за severity, по одному абзацу
на знахідку: `file:line`, скіл-джерело, сценарій відмови, запропонований фікс.
WARNING/SUGGESTION — одним рядком кожна. Без переказу diff-а.

## 9. Механізм блокування

- `.claude/settings.json` (у проєкті його зараз **немає**, створюється разом зі скілом) —
  `PreToolUse` на `Bash`, який викликає `.claude/skills/pr-self-review/scripts/guard-pr.sh`.
- Скрипт читає команду з stdin-payload хука; якщо в ній немає `gh pr create` — `exit 0`.
- Інакше: немає артефакту / артефакт протух / `blocked: true` → `exit 2` + повідомлення
  в stderr з причиною і списком CRITICAL-ів.
- Той самий скрипт як `--check` викликається з CLI, щоб його можна було тестувати без хука.

Оскільки хук стосується `.claude/settings.json`, його правку робимо через скіл
`update-config` — це його зона.

## 10. Структура скіла

```
.claude/skills/pr-self-review/
├── SKILL.md                  # тригери, пайплайн §6, критерій CRITICAL, формат звіту
├── rules/
│   ├── routing.md            # таблиця §5 — єдине місце, де вона живе
│   ├── severity.md           # мапінг чужих шкал + рубрика CRITICAL
│   └── repo-conventions.md   # завжди-увімкнена смуга (іменування, дві копії, лок-файли)
├── scripts/
│   ├── collect-diff.sh       # §4 → список файлів + diff у stdout
│   ├── route-skills.sh       # файли → {скіл: [файли]} JSON за rules/routing.md
│   └── guard-pr.sh           # §9, хук + --check
├── examples.md               # 3–4 пари «знахідка → чому CRITICAL / чому лише WARNING»
└── tile.json                 # як в onion-architecture
```

Плюс рядок у `.claude/skills/README.md` (scope `Process`) і `.claude/pr-self-review/`
у `.gitignore`.

## 11. Фази

1. **Каркас без блокування.** `SKILL.md` + `rules/*` + `collect-diff.sh` + `route-skills.sh`.
   Запуск тільки вручну, вердикт друкується, артефакт пишеться, нічого не блокується.
2. **Калібрування.** Прогін на поточному робочому дереві (≈40 змінених файлів) і ще на
   одному історичному дифі. Мета — нуль хибних CRITICAL; кожен зайвий CRITICAL править
   `rules/severity.md`, а не звіт.
3. **Блокування.** `guard-pr.sh`, `.claude/settings.json` через `update-config`, перевірка
   що `gh pr create` реально падає і що `--force` реально проходить.
4. **Каталог.** Рядок у `.claude/skills/README.md`, `tile.json`, `examples.md`.

## 12. Критерії приймання

- Кожен скіл із `.claude/skills/README.md` або присутній у `rules/routing.md`, або явно
  названий там як «не маршрутизується» (з причиною). Розбіжність = баг скіла.
- На дифі, що чіпає лише `client/**`, жоден бекенд-скіл не запускається — і навпаки;
  карта покриття з кроку 1 це показує.
- Diff без змін → вихід за секунди, без виклику підагентів.
- Штучно внесений CRITICAL (наприклад, `drizzle-orm` у `routes.ts` або контракт в одній
  копії `vendor/shared`) ловиться і блокує `gh pr create`.
- Чистий diff → `blocked: false`, `gh pr create` проходить без втручання.
- Скіл не виконав жодної git-мутації і не запустив жодного тесту.

## 13. Ухвалені рішення

Питання, що були відкритими на етапі плану, закриті так:

- **Гейтиться тільки відкриття PR** — `gh pr create` і `gh pr ready`. `git push` вільний:
  пуш робиться частіше й раніше, блокувати його означало б заважати роботі, а не PR-у.
- **`--scope branch` за замовчуванням** — закомічене в гілці + незакомічене + нові файли.
  `--scope working` лишається як звуження.
- **Звіт пишеться і в markdown** — `.claude/pr-self-review/last-run.md`, придатний для
  вставки в тіло PR; `last-run.json` читає хук.
- **`/code-review` не підключається** — він шукає баги, цей скіл перевіряє конвенції й
  тримає гейт. Дві різні команди, запускаються незалежно.
- **Тести не запускаються за замовчуванням** (діє стандартне правило користувача);
  `--tests` вмикає лише unit-смуги зачеплених пакетів, ніколи `*.it.test.ts` і ніколи e2e.

Відхилення від плану, зроблені під час реалізації:

- Скриптів чотири, не три: додано `write-verdict.sh` — інакше вердикт писала б модель
  руками, а `head_sha`/`dirty_hash` мусять рахуватись машинно.
- Виключені файли (лок-файли, `docs/design/**`, бінарники) не перелічуються поштучно —
  лише `excluded_count`; у `skipped` лишаються тільки файли, завеликі для рев'ю.
- Хук матчить `gh` **у позиції команди**, а не будь-де в рядку, і пропускає команди, що
  самі викликають `guard-pr.sh`: інакше `echo "gh pr create"` або власний тест гейта
  блокують самі себе.
